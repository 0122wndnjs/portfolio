# 개인 외주 프로젝트 관리실 PRD

작성일: 2026-09-23

상태: 초기 기획안 — 현재 구현 범위는 [운영 설정](admin-workspace-setup.md) 참고

## 1. 제품 목적

포트폴리오의 비공개 관리자 영역에서 외주 프로젝트, 프로젝트별 칸반 작업, 마감과 입금 상태를 관리한다. 운영자는 본인 한 명이며, 패스키로 로그인하고 텔레그램으로 필요한 알림을 받는다.

매일 접속했을 때 다음 질문에 빠르게 답할 수 있어야 한다.

- 오늘 어떤 작업을 해야 하는가?
- 어떤 프로젝트가 고객 확인을 기다리고 있는가?
- 가까운 마감과 지연된 작업은 무엇인가?
- 아직 받지 못한 금액과 예정일은 언제인가?

## 2. 범위와 전제

### 사용자 요청으로 정해진 방향

- 기존 포트폴리오에 관리자 페이지 추가.
- 프로젝트별 관리와 칸반보드 제공.
- 패스키 인증 및 텔레그램 연동.

### 이 초안에서 제안하는 기본값

- 단일 관리자 전용. 고객 및 팀원 계정 없음.
- 관리자 주소는 `/admin`, 공개 포트폴리오와 별도 화면 구성.
- 텔레그램은 알림 발송만 제공. 명령 입력과 작업 등록은 후속 범위.
- 입금 관리는 수동 기록. 은행·결제 서비스와 자동 연동하지 않음.
- 통화는 KRW, 기준 시간대는 Asia/Seoul.
- 파일은 외부 저장소 링크로 연결. 직접 업로드는 후속 범위.

### 현재 저장소 확인 결과

현재 `package.json`과 `src/app` 기준 Next.js 16 / React 19 / TypeScript / Tailwind CSS 4 프로젝트다. AGENTS.md의 예시 구조와 달리 현재 확인된 앱은 `client`, `server`로 분리되어 있지 않다. 이 문서는 기존 Next.js 앱 확장을 전제로 한다. DB, 인증 저장소, 배치 실행 환경은 구현 전에 확정한다.

## 3. 메뉴 및 URL 구성

| 메뉴 | URL | 주요 내용 |
| --- | --- | --- |
| 대시보드 | `/admin` | 오늘 할 일, 마감 임박, 고객 확인 대기, 미입금 요약 |
| 프로젝트 | `/admin/projects` | 프로젝트 목록, 검색, 필터, 신규 생성 |
| 프로젝트 상세 | `/admin/projects/[id]` | 개요·칸반·입금·링크/메모 탭 |
| 전체 작업 | `/admin/tasks` | 프로젝트를 가로지르는 작업 목록과 필터 |
| 입금 관리 | `/admin/payments` | 전체 청구 일정, 부분 입금, 미입금 현황 |
| 설정 | `/admin/settings` | 패스키, 복구, 세션, 텔레그램, 알림 설정 |
| 로그인 | `/admin/login` | 패스키 로그인. 사이드바에 표시하지 않음 |

데스크톱은 왼쪽 사이드바와 오른쪽 콘텐츠로 구성한다. 상단에는 현재 화면 제목과 주요 실행 버튼을 둔다. 모바일은 메뉴 버튼으로 내비게이션을 열고 콘텐츠를 전체 너비로 사용한다.

프로젝트 상세의 기본 탭은 칸반이다. 프로젝트 제목과 상태, 마감일은 탭 이동 후에도 상단에 유지한다. 작업 카드는 상세 패널로 열고, 모바일에서는 전체 화면 형태로 표시한다.

## 4. 핵심 사용자 흐름

### 프로젝트 시작

1. 프로젝트 목록에서 새 프로젝트를 생성한다.
2. 프로젝트명, 고객명, 상태를 입력하고 필요하면 마감일과 계약 금액을 지정한다.
3. 프로젝트 칸반에 작업 카드를 추가한다.
4. 입금 탭에 계약금·중도금·잔금 등의 청구 일정을 등록한다.
5. 링크/메모에 계약서, 디자인, 저장소, 배포 주소를 연결한다.

### 매일 작업

1. 대시보드에서 오늘 마감, 지연, 고객 확인 대기를 확인한다.
2. 작업을 열어 체크리스트와 메모를 확인한다.
3. 작업 상태를 이동하고 진행 내용을 기록한다.
4. 고객 응답이 필요하면 확인 대기로 이동한다.
5. 응답 후 수정이 필요하면 진행 중으로, 승인되면 완료로 이동한다.

### 입금 및 프로젝트 종료

1. 청구 항목에 실제 입금 금액과 입금일을 기록한다.
2. 잔액이 남으면 부분 입금 상태와 미입금 잔액을 표시한다.
3. 프로젝트 완료 전 미완료 작업과 미입금 잔액을 안내한다.
4. 사용자가 확인하면 잔여 항목이 있어도 프로젝트를 완료 처리할 수 있다.
5. 완료 프로젝트는 기본 목록에서 분리한다. 미입금 항목은 계속 조회하고 알림을 받는다.

## 5. 화면별 요구사항

### 5.1 대시보드

- 진행 중 프로젝트 수, 지연 작업 수, 확인 대기 작업 수, 전체 미입금 잔액 표시.
- 오늘 마감 작업, 마감이 지난 작업, 7일 이내 마감 작업을 구분.
- 확인 대기 작업에 프로젝트명과 대기 시작일, 경과 일수 표시.
- 7일 이내 입금 예정 항목과 연체 항목 표시.
- 항목 클릭 시 해당 프로젝트 또는 작업 상세로 이동.
- 데이터가 없으면 프로젝트 생성 버튼과 간단한 안내 표시.
- 미입금은 등록된 청구액에서 입금액을 뺀 금액이며, 계약 금액과 다를 수 있음을 명시.

### 5.2 프로젝트 목록 및 개요

필수 입력은 프로젝트명과 고객명이다. 프로젝트명은 1~100자, 고객명은 1~80자이며 공백만 입력할 수 없다. 기본 상태는 준비 중이다.

선택 입력:

- 간단한 설명.
- 고객 연락처 및 이메일.
- 시작일과 마감일.
- 계약 금액.
- 외부 링크 및 메모.

프로젝트 상태는 `준비 중 / 진행 중 / 보류 / 완료 / 취소`로 고정한다. 고객 확인 대기는 작업 상태로 관리한다.

- 카드 또는 목록에 고객, 상태, 마감일, 완료 작업 수/전체 작업 수 표시.
- 프로젝트명·고객명 검색, 상태 필터, 마감순·최근 수정순 정렬 제공.
- 기본 목록은 준비 중·진행 중·보류 프로젝트 표시.
- 완료·취소 프로젝트는 필터로 조회하며 상태를 되돌릴 수 있음.
- 시작일과 마감일이 모두 있으면 마감일은 시작일보다 빠를 수 없음.
- 첫 버전은 프로젝트 영구 삭제를 제공하지 않음. 취소 상태로 정리.

### 5.3 프로젝트 칸반

기본 열:

`할 일 → 진행 중 → 확인 대기 → 완료`

- 모든 열 사이에서 직접 이동 가능. 순서 강제 없음.
- 드래그로 열 이동 및 같은 열 안의 순서 변경.
- 키보드와 모바일 사용자를 위한 상태 선택 메뉴 제공.
- 카드 순서와 상태는 새로고침 후에도 유지.
- 저장 실패 시 이전 상태로 복구하고 재시도 안내.
- 빈 열에서도 작업 추가 가능.
- 첫 버전에는 사용자 정의 열, 하위 작업 계층, 작업 간 의존성 없음.

카드에 표시할 정보:

- 제목.
- 우선순위: 낮음 / 보통 / 높음, 기본 보통.
- 마감일 및 지연 표시.
- 체크리스트 완료 수.
- 확인 대기일 경우 대기 경과 일수.

작업 상세:

- 제목: 필수, 1~200자, 공백만 입력 불가.
- 설명/작업 메모: 일반 텍스트.
- 상태, 우선순위, 선택 마감일.
- 체크리스트 항목 추가·수정·완료·삭제.
- 이름과 URL을 가진 관련 링크.
- 생성일, 수정일, 확인 대기 진입 시각, 완료 시각.
- 작업 보관 및 보관 해제. 보관 작업은 기본 보드와 집계에서 제외.

확인 대기 진입 시각은 해당 상태로 들어갈 때 기록한다. 다른 상태를 거쳐 다시 진입하면 새 시각으로 갱신한다. 완료 시 완료 시각을 기록하고 완료를 취소하면 현재 완료 시각을 비운다.

체크리스트를 모두 완료해도 작업 상태는 자동 변경하지 않는다. 미완료 체크리스트가 있는 작업을 완료하려면 안내 후 확인을 받는다.

### 5.4 전체 작업

- 프로젝트 간 작업을 한 목록에서 조회.
- 프로젝트, 상태, 우선순위, 마감 조건으로 필터.
- 빠른 필터: 오늘 / 7일 이내 / 지연 / 확인 대기 / 마감 없음.
- 각 행에 프로젝트명 표시. 선택 시 작업 상세 열기.
- 상태와 마감일 변경은 프로젝트 칸반에도 반영.
- 기본 조회는 준비 중·진행 중·보류 프로젝트의 미완료·미보관 작업.
- 완료·취소 프로젝트 및 완료 작업은 명시적으로 필터를 선택하면 조회 가능.
- 첫 버전은 목록 형태만 제공. 전체 프로젝트 통합 칸반과 달력은 후속 범위.

### 5.5 입금 관리

프로젝트마다 여러 청구 항목을 등록한다. 예: 계약금 100만 원, 중도금 100만 원, 잔금 200만 원.

청구 항목:

- 항목명, 청구 금액: 필수.
- 입금 예정일, 메모: 선택.
- 입금 내역: 금액, 실제 입금일, 메모. 여러 건 기록 가능.

계산 규칙:

- 청구 금액과 개별 입금 금액은 0보다 큰 원 단위 정수.
- 누적 입금액이 0이면 미입금, 청구액 미만이면 부분 입금, 같으면 입금 완료.
- 첫 버전은 초과 입금 입력을 차단. 청구액을 누적 입금액 아래로 수정할 수 없음.
- 미입금 잔액 = 청구액 − 누적 입금액.
- 예정일이 지났고 잔액이 남으면 연체로 표시. 연체는 입금 상태와 별도 표시.
- 예정일이 없으면 미입금 집계에는 포함하지만 연체로 분류하지 않음.
- 계약 금액과 청구 합계가 다르면 차이를 안내하되 저장은 허용.
- 금액 합산은 서버에서 검증. 새로고침 후에도 동일한 결과 유지.

잘못 입력한 입금 내역은 확인 후 수정·삭제할 수 있다. 금액 변경 이력을 기록한다. 입금 내역이 있는 청구 항목은 바로 삭제할 수 없으며, 먼저 관련 입금 내역을 정정해야 한다. 취소 프로젝트의 청구도 자동 삭제되지 않는다. 더 이상 받지 않을 청구는 입금 내역이 없는 경우 확인 후 삭제한다.

세금 계산, 세금계산서 발행, 회계 장부, 환불 및 외화 처리는 범위 밖이다.

### 5.6 설정

보안:

- 등록된 패스키 목록, 이름, 등록일, 최근 사용일 표시.
- 추가 패스키 등록 및 삭제.
- 마지막 패스키 삭제 차단.
- 복구 코드 발급·재발급, 재발급 시 기존 코드 무효화.
- 현재 세션 로그아웃 및 모든 세션 종료.

텔레그램:

- 연결 상태와 연결된 수신 대상 표시.
- 테스트 알림 발송 및 결과 확인.
- 연결 해제, 알림 전체 활성화/비활성화.
- 알림 종류별 활성화, 일일 요약 시간, 확인 대기 기준 일수 설정.
- 최근 발송 성공·실패 기록과 실패 재시도 제공.

## 6. 패스키 및 접근 제어

- 공개 회원가입 없음. 운영 환경에서 관리자를 최초 1회 생성하는 제한된 절차 마련.
- 최초 패스키 등록에는 만료되는 일회용 등록 권한 필요. 임의 방문자가 첫 관리자가 될 수 없어야 함.
- 기기의 지문·얼굴·PIN 등 사용자 확인을 요구하는 패스키 인증 설계.
- 지문·얼굴 원본은 앱에서 수집하거나 저장하지 않음.
- 등록 및 인증 요청의 challenge, origin, RP ID, 사용자 확인 결과를 서버에서 검증.
- 인증 라이브러리와 RP ID는 실제 운영 도메인 및 배포 환경 확인 후 선정.
- 관리자 페이지뿐 아니라 모든 관리자 데이터 API에서 세션과 관리자 권한 검사.
- 민감 데이터는 공개 페이지 생성 결과, 클라이언트 번들, sitemap, 공유 캐시에 포함하지 않음.
- `/admin` 검색 노출 제한은 보조 수단이며 접근 제어를 대체하지 않음.
- 세션 쿠키는 HttpOnly, Secure, 적절한 SameSite 정책 적용. 상태 변경 요청은 CSRF 방어.
- 제안 기본값: 7일 절대 세션 만료. 패스키·복구·텔레그램 수신 대상 변경 시 최근 5분 이내 재인증 요구.
- 복구 코드는 일회용이며 서버에는 해시만 저장. 최초 발급 시에만 원문 표시.
- 복구 성공 후 제한된 절차로 새 패스키를 등록하고 기존 세션을 모두 종료.
- 인증 및 복구 시도에 속도 제한 적용. 패스키와 복구 수단을 모두 잃은 경우 운영자 복구 절차를 별도로 문서화.

## 7. 텔레그램 알림

### MVP 알림 종류

| 종류 | 제안 기본값 | 대상 |
| --- | --- | --- |
| 일일 요약 | 매일 09:00 | 오늘 마감, 지연, 확인 대기, 입금 예정·연체 건수 |
| 작업 마감 | 전날 09:00 및 당일 09:00 | 미완료·미보관 작업 |
| 확인 대기 장기화 | 진입 후 3일 경과 시 1회 | 아직 확인 대기인 작업 |
| 입금 예정 | 예정일 09:00 | 잔액이 남은 청구 |
| 입금 연체 | 예정일 다음 날 09:00, 이후 일일 요약에 포함 | 잔액이 남은 청구 |

- 작업 알림은 준비 중·진행 중 프로젝트에 적용. 보류·완료·취소 프로젝트의 작업 알림은 중지.
- 입금 알림은 프로젝트 상태와 무관하게 잔액과 예정일 기준으로 발송.
- 전송 직전에 최신 상태를 다시 확인해 완료·보관·입금 완료된 항목의 발송을 취소.
- 일일 요약은 내용이 없으면 발송하지 않음.
- 기본 메시지에는 종류, 프로젝트명, 작업/청구 제목, 날짜, 관리자 링크만 포함. 금액과 상세 메모는 제외.
- 링크 접근에는 로그인 필요. 링크에 인증 토큰이나 고객 개인정보를 포함하지 않음.
- 봇 토큰은 서버 비밀 저장소에 보관. 브라우저로 전달하지 않음.
- 관리자 설정에서 생성한 만료되는 일회용 연결 코드로 본인의 개인 채팅을 연결. 임의의 채팅에서 수신 대상을 변경할 수 없음.
- 스케줄러 재실행 시 알림 기록을 이용해 중복 발송 방지. 대기 재진입은 새 알림 주기로 취급.
- 마감 변경 시 기존 예약을 취소하고 새 날짜 기준으로 예약. 등록 시 이미 지난 발송 시각은 소급 개별 발송하지 않고 다음 요약에 포함.
- 일시 실패는 지수 백오프로 최대 3회 재시도. 연결 거부 등 영구 오류는 즉시 실패 처리.
- API 응답 유실로 발송 여부가 불명확한 경우 중복 가능성을 기록하고 무조건 재전송하지 않음.
- 실패해도 작업·입금 데이터 저장은 성공해야 함. 설정에 실패 원인과 재시도 동작 제공.

## 8. 데이터 개념 및 영향도

아래는 논리 모델이며 실제 DB 스키마나 마이그레이션은 이 문서에서 확정·적용하지 않는다.

| 개념 | 주요 데이터 |
| --- | --- |
| 관리자 | 단일 운영자 식별자 |
| 패스키 | 소유 관리자, credential ID, 공개키, 검증 메타데이터, 이름, 사용 시각 |
| 세션·복구 코드 | 만료·폐기 상태, 복구 코드 해시 |
| 프로젝트 | 고객 정보, 상태, 일정, 계약 금액, 메모 |
| 작업 | 프로젝트, 제목, 상태, 우선순위, 순서, 마감, 대기·완료 시각, 보관 상태 |
| 체크리스트 | 작업, 내용, 완료 여부, 순서 |
| 관련 링크 | 프로젝트 또는 작업, 이름, URL |
| 청구 항목 | 프로젝트, 이름, 청구액, 예정일 |
| 입금 내역 | 청구 항목, 금액, 입금일, 메모 |
| 알림 설정·발송 기록 | 수신 대상, 종류별 설정, 대상 이벤트, 중복 방지 키, 결과 |
| 변경 이력 | 인증 수단·수신 대상·금액 변경 주체, 시각, 변경 내용 |

신규 영속 저장소가 필요하다. 기존 공개 포트폴리오 데이터와 독립적으로 저장하며 공개 프로젝트 목록에 외주 프로젝트가 자동 게시되지 않게 한다. 고객 정보와 금액이 추가되므로 서버 권한 검사, 백업, 복구 절차가 필수다. 구현 단계에서 실제 스키마 변경 전 영향도를 다시 설명한다.

## 9. 공통 UX 및 품질 요구사항

- 데스크톱과 모바일에서 프로젝트 생성, 작업 상태 변경, 입금 기록 가능.
- 360px 너비에서도 주요 버튼과 입력을 사용할 수 있어야 함. 칸반은 열 선택 방식 또는 보드 영역 가로 스크롤 제공.
- 로딩, 빈 결과, 저장 성공, 저장 실패, 세션 만료 상태를 구분.
- 중복 제출 방지. 저장 실패 시 입력 내용 유지.
- 날짜만 있는 마감은 서울 시간 기준 해당 날짜가 끝나면 지연 처리.
- 마감 없는 항목은 날짜 기반 알림에서 제외.
- 모바일·다른 탭의 수정 충돌을 감지하면 덮어쓰기 전에 새로고침 안내.
- 드래그 없이도 주요 작업 수행 가능. 폼 레이블, 키보드 포커스, 상태 텍스트 제공.
- 삭제·취소·금액 변경은 영향 범위를 확인할 수 있도록 안내.
- 서버 로그에 봇 토큰, 세션 값, 복구 코드, 고객 메모 원문을 남기지 않음.
- 제안 백업 기준: 일 1회, 최근 30일 보관. 출시 전에 실제 복원 검증.
- 공개 포트폴리오의 라우트와 콘텐츠, 모바일 표시를 유지.

## 10. MVP 수용 기준

1. 비로그인 상태에서 관리자 URL 또는 API에 직접 접근해도 비공개 데이터를 받을 수 없다.
2. 최초 관리자 등록 권한 없이 패스키를 등록할 수 없다.
3. 패스키 로그인, 추가 등록, 마지막 패스키 삭제 차단, 복구 코드 일회 사용이 검증된다.
4. 프로젝트 생성·수정·검색·상태 필터가 동작하고 새로고침 후 유지된다.
5. 칸반 이동 및 순서 변경이 저장되고, 실패 시 화면 상태가 복구된다.
6. 드래그 없이 모바일과 키보드로 작업 상태를 변경할 수 있다.
7. 전체 작업에서 변경한 상태와 마감이 프로젝트 화면에 동일하게 반영된다.
8. 확인 대기 진입·재진입·해제 시 경과 일수와 알림 대상이 갱신된다.
9. 분할 입금, 부분 입금, 연체 계산이 정확하며 초과 입금과 잘못된 금액은 거부된다.
10. 프로젝트 완료·취소 후에도 미입금 잔액이 사라지지 않는다.
11. 텔레그램 연결·테스트 발송·해제가 동작하고 스케줄 재실행이 중복 예약을 만들지 않는다.
12. 텔레그램 장애가 작업 저장을 막지 않고 실패 이력을 확인할 수 있다.
13. 서울 시간 기준 오늘·지연·알림 경계가 일관된다.
14. 공개 포트폴리오가 정상 동작하고 비공개 데이터가 공개 산출물에 포함되지 않는다.
15. 배포 환경의 인증, 영속 저장, 예약 알림, 백업 복원을 검증한다.

## 11. 구현 순서

### 1단계 — 관리자 접근 및 기본 구조

배포 환경·DB·인증 방식을 확정하고 최초 등록, 패스키 로그인, 복구, 관리자 레이아웃, 서버 권한 검사를 구현한다. 검증 목표는 실제 운영 도메인에서 본인만 접근 가능한 빈 관리실이다.

### 2단계 — 프로젝트와 칸반

프로젝트 목록·상세, 칸반, 작업 상세, 체크리스트, 전체 작업을 구현한다. 검증 목표는 프로젝트 하나를 등록하고 모바일과 데스크톱에서 작업을 계속 관리할 수 있는 상태다.

### 3단계 — 입금과 대시보드

청구·입금 기록, 잔액 계산, 마감·대기·미입금 집계를 구현한다. 검증 목표는 대시보드만으로 당일 작업과 받아야 할 금액을 확인하는 것이다.

### 4단계 — 알림과 운영 검증

텔레그램 연결, 예약 발송, 실패 기록, 백업·복원 검증을 완료한다. 1~4단계를 충족하면 MVP 출시로 본다.

## 12. 후속 범위

- 포트폴리오 문의 접수 → 프로젝트 후보 등록 → 텔레그램 알림.
- 텔레그램 메시지로 작업 추가 및 상태 변경.
- 반복 작업, 달력, 사용자 정의 칸반 열.
- 파일 업로드, 고객별 이력, 견적·계약서 관리.
- 고객용 진행 현황 공유 화면 및 제한된 접근 권한.
- 기간별 매출·입금 리포트, 데이터 내보내기.

## 13. 출시 전 확정 항목

- 운영 도메인과 배포 환경, 패스키 RP ID.
- DB와 백업 저장 위치, 예약 실행 수단.
- 최초 관리자 등록 및 모든 인증 수단 분실 시 운영 복구 절차.
- 텔레그램 봇·수신 계정, 알림에 노출할 정보 범위.
- 세션 만료, 확인 대기 기준, 알림 시간의 제안 기본값 채택 여부.

성공 기준은 등록 기능의 수가 아니라 실제 외주 프로젝트를 매일 관리할 수 있는지다. 초기 2주 동안 실제 프로젝트를 사용하며 누락된 마감·입금, 알림 피로도, 반복 입력 구간을 확인하고 다음 범위를 정한다.
